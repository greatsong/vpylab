“작은 코드가 자기 작품으로 이어지는 경험”을 보여줍니다.

VPyLab의 가장 설득력 있는 방향은 “Python으로 빛과 소리를 만들며 코딩을 배우고, 만든 부품을 자기 3D 작품으로 발전시키는 교실”입니다. 브라우저 실행·Python·3D·소리·로그인 없는 체험 중 어느 하나를 세계 최초의 기능으로 내세우기보다, 작은 체험에서 작품 제작과 설명으로 이어지는 연결을 강점으로 보여주는 편이 정확합니다.

해외 서비스가 잘하는 것은 서로 다릅니다. TunePad는 익숙한 곡을 Python 개념과 연결하고, EarSketch는 코드와 음악의 시간 구조를 함께 보여줍니다. Strudel은 재생 중인 부분을 표시해 코드와 소리의 관계를 드러내며, Hydra는 짧은 표현을 즉시 시각 결과로 돌려줍니다. Web VPython은 물리·수학의 현상을 소수의 3D 명령으로 표현하고, Delightex는 완성된 공간과 이야기를 먼저 체험하게 합니다.

이 자료를 모두 VPyLab에 통째로 붙일 필요는 없습니다. 현재 Three.js·Web Audio·Pyodide 기반을 유지하면서 좋은 학습 장면을 가져오는 것이 우선입니다. “한 값만 바꾸면 결과가 어떻게 달라지는가”, “지금 들리는 음이 어느 코드·물체와 연결되는가”, “친구가 만든 것을 출처와 함께 다시 쓸 수 있는가”를 기준으로 고르면 기능의 복잡도를 통제할 수 있습니다.

현재 진행 중인 네 개선은 이 방향과 맞습니다. 실습 엔진의 10분 재사용은 학습 중 왕복을 편하게 하고, 오디오 시각 예약과 현재 음 표시는 박자·관찰을 돕습니다. 정지 장면의 GPU 그리기 축소는 불필요한 자원 사용을 줄이며, 우주 악기·빛나는 아르페지오는 실제로 보여줄 작품을 만듭니다. 다만 로컬 구현과 실제 배포·학교 기기 검증은 구분해야 합니다.

다음 투자는 새 최상위 메뉴나 복잡한 음악 편집기를 추가하는 것보다 대표 작품 2~4개의 교육 품질과 실행 신뢰성을 높이는 데 쓰는 편이 좋습니다. 학생이 5분 안에 첫 소리나 빛을 바꾸고, 20분 안에 자기 선택이 담긴 작품을 만들며, 수업 끝에 바꾼 코드와 관찰 근거를 설명하게 만드는 것이 제품과 마케팅 모두에 도움이 됩니다.

현재 상태 · 로컬 구현과 다음 제안을 구분합니다.

앞서 승인하신 1~4 개선은 로컬 구현·검증을 마쳤습니다. 전체 클라이언트 85개 파일·879개 검사, 실제 브라우저 12개 시나리오가 통과했습니다. 정지 장면은 1.1초 동안 2회, 카메라 조작 중에는 40회 그렸습니다. 전체 실행에서 시간 제한에 걸린 문서 예제 1건은 빌드 종료 후 분리 재실행해 통과했습니다. 운영 배포·브라우저 검증은 마쳤으며 학교 실기기 측정은 남아 있습니다.

TunePad

해외의 강점
Python 문법을 곡의 구성과 직접 연결하는 교육 설계가 뚜렷합니다. 공식 튜토리얼은 곡마다 반복·리스트·조건·함수 같은 초점을 제시합니다. 학생은 추상적인 문법 설명을 읽기 전에 들어보고 싶은 결과를 먼저 만납니다.
우리의 강점
VPyLab은 음의 구성에 3D 위치·크기·빛·입력 반응을 함께 묶을 수 있습니다. 같은 리스트를 음과 물체에 연결하면 리스트 인덱스가 단지 곡의 순서가 아니라 공간의 선택도 바꾼다는 점을 탐구할 수 있습니다.
남은 차이
음악 제작의 깊이와 여러 트랙을 다루는 경험에서는 TunePad를 바로 따라잡았다고 보기 어렵습니다. 단순히 음을 내는 API가 있다는 사실만으로 음악 교육 콘텐츠의 수준이 같아지는 것도 아닙니다.
구체적 행동
유명곡 자체를 복제해 대표 자산으로 삼기보다, 아르페지오·폴리리듬·랜덤 비트 같은 학습 구조를 오리지널 선율로 옮깁니다. 각 작품 소개에 “이 활동에서 바꾸는 Python 개념”을 하나씩 명시합니다.

EarSketch

해외의 강점
Python 또는 JavaScript 코드, 소리 자료, 여러 트랙의 시간 구조와 교재가 하나의 음악 작업 환경으로 연결됩니다. 코드가 음악 구성에 어떻게 반영되는지를 시간축에서 볼 수 있다는 점이 중요합니다.
우리의 강점
VPyLab은 시간축 중심 음악 제작보다 짧은 코드로 만든 물체·빛·소리의 반응을 동시에 관찰하게 하는 데 집중할 수 있습니다. 3D 신호 장치나 움직이는 악기는 서로 다른 교과 개념을 한 작품에서 연결하기 좋습니다.
남은 차이
샘플 라이브러리와 음악 편곡 환경의 폭은 현재 VPyLab의 주요 강점이 아닙니다. 전문 음악 제작 수준이나 같은 양의 수업 지원 자료를 제공한다고 주장할 근거도 부족합니다.
구체적 행동
전체 DAW를 만드는 대신 8~16단계의 작은 연주 표시, 현재 음·길이·쉼의 구분부터 제공합니다. 교사 자료에는 예상 시간, 필요한 개념, 관찰 질문, 결과물 예시를 한 장으로 정리합니다.

Strudel

해외의 강점
아주 짧은 패턴을 실행하며 반복·쉼·겹침을 탐색하게 하고, 연주 중인 코드 부분이나 피아노롤을 시각화합니다. 소리가 빠르게 지나가도 코드와 연결해 이해할 발판이 있습니다.
우리의 강점
VPyLab에서는 Python의 실제 리스트·반복문·함수가 작품의 규칙이 되므로 일반 Python 학습으로 이어지는 설명을 만들기 쉽습니다. 공간 속 여러 물체와 선택 관계를 함께 다룰 수도 있습니다.
남은 차이
현재 음 이름 표시는 시작점일 뿐 Strudel의 코드 범위 강조나 패턴 시각화 전체와 같지 않습니다. VPyLab의 Python 실행과 오디오 예약이 서로 다른 시간 체계를 갖는 부분도 명확히 다뤄야 합니다.
구체적 행동
우선 학습용 작품의 음 목록과 재생 위치만 연결해 보입니다. 일반 Python 모든 줄을 실시간 추적하는 대규모 기능은 뒤로 두고, 소리 경계와 표시 경계가 실제로 맞는지 측정합니다.

Hydra

해외의 강점
시각 소스에 변형을 이어 붙이는 짧은 표현으로 큰 화면 변화를 만듭니다. 공식 입문 문서 자체의 코드 블록도 수정할 수 있어 읽기와 실험 사이의 거리가 짧습니다. 마이크 분석값을 시각 변수에 연결하는 자료도 제공합니다.
우리의 강점
3D 물체의 위치·크기·색과 Python 이름·조건·반복의 관계를 명시적으로 보여주기 좋습니다. 즉흥 시각 공연보다 교실의 설명 가능한 실험과 재사용 가능한 부품에 초점을 둘 수 있습니다.
남은 차이
한 줄의 시각적 놀라움이나 영상 합성의 폭에서는 별도 콘텐츠 설계가 필요합니다. Hydra 전체를 내장하면 언어·실행 체계·GPU 비용까지 늘어나 현재 복잡도 고민과 충돌할 수 있습니다.
구체적 행동
한 값만 바꾸는 큰 시각 차이, 바로 실행하는 문서, 결과를 비교하는 구성을 배웁니다. 오디오 분석은 내부 합성 소리의 크기·저중고역 같은 작은 값부터 선택 기능으로 검토하고, 마이크 권한이 필요한 활동을 기본 입문으로 삼지 않습니다.

p5.js

해외의 강점
창작 코딩과 교육을 연결하는 예제·참조·공동체의 폭이 큽니다. 애니메이션·오디오·WebGL을 다양한 수준에서 시작할 수 있고, 예제 중심의 학습 진입점이 풍부합니다.
우리의 강점
VPyLab은 일반 창작 코딩의 폭을 모두 다루기보다, Python과 3D·빛·소리를 함께 다루는 한 수업의 경로를 더 촘촘히 제공할 수 있습니다. 한글 안내와 표준 Python 의미를 유지하는 교실용 재료가 유용할 수 있습니다.
남은 차이
예제 수와 생태계의 폭을 정면으로 경쟁하기 어렵습니다. 한국어 지원 자체도 오직 VPyLab만의 기능이라고 주장해서는 안 됩니다. 초심자가 처음 무엇을 열어야 하는지 분명한 큐레이션이 필요합니다.
구체적 행동
예제마다 학습 개념, 첫 수정, 다음 실험을 붙이고 대표 작품을 적게 유지합니다. p5.js로 만든 원본 작품을 통째로 옮기기보다 그 활동이 드러내는 입력→규칙→출력 구조를 VPyLab의 API로 다시 설계합니다.

Web VPython

해외의 강점

우리 콘텐츠에 가져올 8가지 원칙

PRINCIPLE 01

완성된 결과를 먼저 보고, 작은 수정으로 들어갑니다

TunePad의 곡별 튜토리얼과 Delightex의 작품 중심 소개는 만들고 싶은 결과를 진입점으로 삼습니다.

적용
첫 카드에서 짧은 완성 장면과 조작법을 보여주고, 실습을 열면 같은 작품의 시작 코드가 준비되게 합니다. 첫 과제는 음 하나·반지름 하나·순서 하나로 좁힙니다.
설계 점검
아름다운 영상을 보여준 뒤 학생에게 빈 코드 창만 주거나, 첫 수정에 여러 개념을 동시에 요구하지 않습니다.
완료의 증거
처음 온 학생이 교사 대리 조작 없이 작품을 실행하고 한 값을 바꿔 차이를 찾습니다. 관측 목표는 5분 안의 첫 의미 있는 수정이며 실제 수업에서 확인해야 합니다.

PRINCIPLE 02

눈에 보이는 피드백은 정답 표시보다 원인 설명을 돕게 합니다

Strudel은 현재 패턴 부분과 연주 시각을 함께 보여주는 기능을 제공합니다.

적용
음 이름·현재 선택 물체·연주 진행을 같은 근거에서 표시합니다. “재생 예약됨”과 “지금 들림”을 구분하고, 소리를 꺼도 크기·위치·글자로 변화를 읽게 합니다.
설계 점검
색만 바뀌는 점멸이나 성공 점수만으로 이해했다고 판단하지 않습니다. 아직 들리지 않은 다음 음을 현재 음처럼 미리 표시하지 않습니다.
완료의 증거
학생이 “이 음이 들릴 때 이 물체가 선택되는 이유는 같은 인덱스를 쓰기 때문”이라고 설명하고, 음 목록과 색 목록을 따로 바꾸는 실험을 합니다.

PRINCIPLE 03

예상·실행·수정·설명은 하나의 짧은 사이클로 묶습니다

Hydra 입문은 값을 바꾸고 다시 실행하며 결과를 확인하는 문서 구성을 사용하고, TunePad는 음악적 목표와 코드 개념을 연결합니다.

적용
각 활동을 “먼저 예상하기 → 실행하기 → 한 가지 바꾸기 → 관찰 기록 → 다른 상황에 적용”의 공통 문장 구조로 통일합니다.
설계 점검
코드 복사와 실행 횟수만으로 완료 처리하거나, 모든 줄을 이해해야 첫 실행을 허용하는 설명을 하지 않습니다.
완료의 증거
활동마다 실제 관찰 문장 하나와 변경한 코드 한 부분이 남습니다. 학생 설명은 서로 달라도 관찰 근거와 코드의 관계가 맞으면 성취로 봅니다.

PRINCIPLE 04

소리는 시간을 다루는 매체이므로 시간 구조도 가르칩니다

EarSketch의 다중 트랙 시간축과 Tone.js의 공유 시간 기준은 재생 순서와 박자를 코드와 연결합니다.

적용
음의 길이, 다음 음까지의 간격, 반복 주기를 따로 설명합니다. 예를 들어 duration=beat*0.85는 발음 길이이고 sleep(beat)는 다음 장면으로 넘어가기까지의 간격임을 비교합니다.
설계 점검
모든 타이머가 같거나, Python sleep으로 호출하는 음악과 오디오 시각에 예약한 시퀀스의 정밀도가 같다고 설명하지 않습니다.
완료의 증거
박자를 늦춰도 음 높이는 그대로라는 실험과, 음 사이의 쉼만 바꾸는 실험을 구분해 할 수 있습니다.

PRINCIPLE 05

흥미로운 문화적 소재는 쓰되 대표 자산은 자기 것으로 만듭니다

TunePad는 여러 대중음악 튜토리얼을 제시합니다. 이는 친숙한 결과가 학습 동기가 될 수 있는 설계 사례입니다.

적용
공식 예제는 해당 서비스에서 열어 분석하게 하고, VPyLab의 광고·대표 콘텐츠는 오리지널 캐릭터·선율로 만듭니다. 학습 구조인 아르페지오·반복·랜덤 선택을 가져옵니다.
설계 점검
외부 튜토리얼의 공개 열람을 음악·영상·캐릭터의 재배포 허락으로 간주하지 않습니다. 다른 서비스의 코드를 출처 없이 자체 예제로 소개하지 않습니다.
완료의 증거
대표 예제마다 오리지널 제작 여부·참고 링크·확장 명령의 범위가 정리되어 있으며, 학생 포크에서도 원본 출처가 이어집니다.

PRINCIPLE 06

자료와 실습의 왕복을 제품의 기본 행동으로 봅니다

Hydra 문서는 편집기와 함께 보며 실험하도록 안내하고 EarSketch는 교재와 작업 환경을 연결합니다.

적용
교재·문서·실습을 오가도 코드 초안이 보존되고, 같은 탭에서 실행 환경 준비를 반복하지 않게 합니다. 돌아가기 링크는 원래 단계와 실험 맥락을 유지합니다.
설계 점검
첫 화면 수치만 줄이기 위해 매 실습 진입의 대기를 늘리거나, 안내를 읽으러 갔다가 코드가 초기화되는 경험을 만들지 않습니다.
완료의 증거
실습 → 튜토리얼 → 외부 참고 탭 → 실습의 시나리오에서 작성 중 코드·단계가 유지되고 엔진은 정해진 범위 안에서 재사용됩니다.

PRINCIPLE 07

기능을 더하기 전에 한 작품의 품질을 끝까지 확인합니다

해외 서비스의 강한 인상은 기능 목록뿐 아니라 바로 열리는 대표 콘텐츠와 설명 자료에서 옵니다. 이는 여러 공식 예제의 구성을 비교한 제품적 추론입니다.

적용
대표 예제는 실행·입력·정지·다시 실행·화면 크기 변경·무음 사용·친구의 해석까지 검수합니다. 신규 API보다 이 검수 흐름을 먼저 갖춥니다.
설계 점검
새 메뉴·프레임워크·라이브러리를 동시에 늘리거나 예제 수만 늘려 학습 품질을 대체하지 않습니다.
완료의 증거
교사가 별도 수정 없이 한 차시의 재료로 사용할 수 있고, 실행 오류뿐 아니라 화면과 상호작용의 의도가 확인됩니다.

PRINCIPLE 08

대표 결과물은 남이 읽을 수 있는 설명과 함께 남깁니다

p5.js·Web VPython의 공개 예제와 Hydra의 공유 링크는 작품을 보고 코드를 살펴볼 진입점을 제공합니다.

적용
갤러리의 작품 설명에는 무엇을 만들었는지, 어떤 값을 바꿨는지, 원본과 무엇이 다른지, 친구 피드백으로 무엇을 고쳤는지를 짧게 남기게 합니다.
설계 점검
좋아요·완료율·스크린샷만으로 학습의 깊이를 대신하지 않습니다.
완료의 증거
작품 링크를 받은 다른 학생이 실행하고 코드의 한 부분을 이해해 수정할 수 있습니다. 저장 이력은 결과만이 아니라 선택의 이유를 설명하는 자료가 됩니다.

대표 콘텐츠를 수업으로 완성하는 방법

15분 제안

15분: 네 행성으로 보내는 우주 신호

목표 리스트의 음과 선택 인덱스가 연결됨을 관찰하고, 음 하나를 바꾼 영향을 설명합니다.

출발 조건 실행·정지 버튼 사용과 따옴표 안의 글자를 구별할 수 있으면 시작할 수 있습니다. 목록·함수의 모든 문법을 먼저 완주할 필요는 없습니다.

  1. 0~3분: 완성된 우주 악기를 연주합니다. 키보드와 화면 버튼이 같은 행성을 선택하는지 확인합니다.
  2. 3~6분: notes의 E4를 Eb4로 바꾸기 전에 결과를 예상합니다. 색과 크기까지 변할 것인지도 따로 적습니다.
  3. 6~10분: 음 하나만 바꿔 원본과 비교하고, 선택 물체와 소리가 같은 인덱스로 묶이는 줄을 찾습니다.
  4. 10~13분: 네 번의 입력으로 자기 신호를 만들고 친구가 보고 또는 듣고 따라 하게 합니다.
  5. 13~15분: 친구가 혼동한 부분 하나를 고치고 “나는 ___를 바꾸었고 ___가 달라졌다”를 남깁니다.

남길 결과 변경한 음 목록, 4음 신호의 순서, 관찰 문장 한 개.

관찰할 증거

  • 소리·색·크기의 원인을 서로 다른 코드에서 찾는가
  • 한 번에 한 변수를 바꾼 비교를 했는가
  • 친구의 해석을 듣고 수정 이유를 설명하는가

다른 참여 방법 소리를 끄고 크기·위치·음 이름을 보며 순서를 재현할 수 있습니다. 키보드 사용이 어려우면 버튼을 사용합니다.

45분 제안

45분: 빛으로 읽는 아르페지오

목표 음 목록, 순서 목록, 시간 값의 역할을 구분하고 반복 규칙이 있는 자기 선율을 만듭니다.

출발 조건 리스트 인덱스 0~3과 반복문 안의 들여쓰기를 살펴봅니다. 음악 이론을 선행 조건으로 두지 않습니다.

  1. 0~5분: 8음 완성작을 보고 들으며 오르내리는 흐름을 손으로 따라갑니다.
  2. 5~12분: notes와 반복문 뒤의 숫자 목록을 비교합니다. 음 재료와 선택 순서가 다른 자료라는 점을 찾습니다.
  3. 12~20분: beat만 바꾸고 음 높이·연주 속도·빛 유지 시간의 변화를 구분합니다.
  4. 20~30분: 숫자 0~3으로 자기 8음 순서를 만들고 제목을 붙입니다.
  5. 30~38분: 친구에게 소리를 끈 버전과 켠 버전을 차례로 보여주고 느낌·구별 가능성을 듣습니다.
  6. 38~45분: 순서 또는 간격 하나를 개선하고 원본과 다른 점을 설명합니다.

남길 결과 오리지널 8음 패턴과 작품 제목, 수정 전후 비교, 피드백에 따른 개선 한 개.

관찰할 증거

  • 목록의 값과 인덱스를 혼동하지 않는가
  • duration과 다음 음 간격을 구별하는가
  • 관찰 근거로 자기 선택을 설명하는가

다른 참여 방법 빛의 크기·위치·라벨로 순서를 읽습니다. 친구와 연주자·관찰자 역할을 교대하고, 소리 없는 상태에서도 과제를 완성할 수 있습니다.

45분 × 2회 제안

2차시: 내 부품으로 만든 빛·소리 전시

목표 대장간 부품을 프로젝트에서 재사용하고 입력·상태·출력 규칙을 설계하며 출처를 남깁니다.

출발 조건 함수 호출과 object의 위치·색을 바꾸는 예제를 경험한 학생에게 적합합니다. 팀은 한 기기를 기준으로 차례로 편집·저장합니다.

  1. 1차시 도입: 서로 다른 신호·악기·전시물 중 하나의 사용 상황을 정합니다. 누구에게 무엇을 전달하는지 한 문장으로 씁니다.
  2. 대장간에서 부품 하나를 만들고 생성된 함수와 사용 코드를 실습으로 가져옵니다. 모양의 변수와 상호작용의 변수를 구별합니다.
  3. 입력 두 개 또는 상태 두 개를 정하고 색 외에 크기·위치·라벨로도 구별되게 만듭니다. 소리는 선택 출력으로 붙입니다.
  4. 2차시 도입: 다른 팀에게 작품의 뜻을 먼저 설명하지 않고 사용하게 합니다. 의도와 다른 해석을 기록합니다.
  5. 오해한 상태 하나를 수정하고 코드 또는 저장 이력에 이유를 남깁니다. 참고 모듈과 프로젝트 링크를 확인합니다.
  6. 짧은 전시에서 실행·정지·수정 과정을 보여주고, 각 구성원이 자기가 바꾼 코드와 동료 의견으로 달라진 결정을 설명합니다.

남길 결과 조작 가능한 프로젝트, 상태 약속표, 참고 출처, 사용 시험 기록, 한 번 이상의 개선.
