# 3팀 검토: 공개 프로젝트 리믹스 협업 경로

검토일: 2026-10-28. 검토 대상: `codex/classroom-v2`의 현재 구현과 공개된 공식 VPython 예제. 이 문서는 코드 검토·원문 확인·제한된 호환성 실행 결과이며 실제 학생의 수업 관찰 결과는 아니다. 로컬 HTTP 협업 리허설은 팀별 합성 학생 2명과 공통 교사 계정으로 진행하며 결과는 총괄 보고서와 함께 읽는다. 외부 저장소에 포크·이슈·PR을 생성하거나 다른 학생 GitHub 계정으로 인증하지 않았다.

**판정: 교사가 출처와 호환성을 준비하면 팀 협업 학습에 활용할 수 있다. 공개 프로젝트를 선택하고 원작 계보·라이선스·학생 기여를 자동 관리하는 완성된 리믹스 경로는 아직 없다.** 원작 이해와 작은 개선을 평가해야 하며, 원작 코드 전체의 분량이나 완성도를 학생 실력으로 평가하면 안 된다.

## 학생에게 적절한 변경 범위

권장 질문은 **“공의 크기나 처음 움직임을 바꾸어도 공이 벽 밖으로 나가지 않는가?”**이다. 첫 단계에서는 학생이 새 클래스·함수·목록·복잡한 수학식을 작성하지 않는다.

- 원작의 공 생성 22줄에서 반지름과 색을 읽고, 24줄의 세 숫자가 어느 방향의 움직임에 관계하는지 예측한다.
- 첫 변경은 **반지름 한 값**으로 제한한다. 두 번째 학생은 초기 위치 또는 한 축의 운동량 한 값만 바꿔 비교한다.
- 26줄의 충돌 경계가 공의 반지름을 포함한다는 점을 그림으로 먼저 설명한다. 원작의 `p / mass`는 교사 제공 영역으로 두고 필요할 때 속도와의 관계만 설명한다.
- 31·33·35줄의 연속 비교와 부정은 입문자가 스스로 만들어야 할 문법으로 요구하지 않는다. 먼저 “안쪽이면 계속, 바깥이면 방향 바꾸기”를 두 경우 표로 풀어 읽는다.
- 선택 심화는 경계 조건을 `x >= side or x <= -side`와 비교해 설명하는 정도로 제한한다. 기능을 늘리는 것보다 같은 결과를 쉬운 문법으로 설명하는 데 목적을 둔다.

색만 바꾸는 작업은 조작 연습으로는 가능하지만 창조적 문제 해결의 최종 과제로는 부족하다. 가설 → 작은 변경 → 경계 사례 → 동료 반론 → 새 문맥 적용이 있어야 한다.

## 호환성 확인에서 발견한 실제 문제

원작 20줄의 `color.gray(0.7)`은 그대로 실행되지 않는다. VPyLab은 `color.gray`를 벡터 상수로 정의한다(`client/src/engine/vpython-api.py:210`). 공식 VPython 예제에서 사용하는 함수 호출과 다르므로 **`TypeError: 'vector' object is not callable`을 재현했다.**

교사가 준비한 실행용 복사본에서는 해당 호출만 `vector(0.7, 0.7, 0.7)`로 바꾸면 된다. 이 변경은 학생의 탐구 성과와 분리하여 “교사 준비: 실행 환경 호환 수정”으로 기록한다. 보존한 원작 파일은 바꾸지 않는다.

검증 범위는 다음과 같다.

| 확인 | 결과와 범위 |
| --- | --- |
| 원작 Python 문법 검사 | 통과 |
| 실제 VPyLab Python API에 원작 실행 | 위 TypeError 재현 |
| 한 줄 호환 수정 후 움직임 | CPython에서 실제 `vpython-api.py`를 로드하고 JS 전송만 대체, 대기 없는 제한 반복으로 1,200회 실행. 객체 생성 명령 6개, 축별 방향 반전 x 8회·y 12회·z 14회 확인 |
| 미확인 | Pyodide에서의 실시간 실행, Three.js 렌더링·카메라·궤적 보관 개수·실제 속도·학생 기기별 성능 |

결과는 `.local/project-path-review/public-source/compatibility.json`에 보존했다. 위 제한 실행은 브라우저 실습 성공의 증거를 대신하지 않는다. `scene.caption`도 VPyLab에서는 출력으로 대체된다(`vpython-api.py:1840`). 원작의 영어 카메라 설명을 그대로 보여주기보다 교사가 현재 VPyLab 조작법을 안내해야 한다. 원작의 주석 속 외부 스크립트 예시는 실행하지 않으며 과제 범위에서도 제외한다.

### 현재 가능한 정직한 수동 시작 방법

1. 교사는 고정 원작과 라이선스를 먼저 확인하고 실행용 복사본에 호환 수정 한 줄만 적용한다. 원작 사본과 실행용 복사본을 구분한다.
2. 일반 프로젝트를 만들고 문제 정의에 “공개 프로젝트 리믹스”와 고정 원작 URL·SHA·상대 경로·라이선스 URL을 적는다. 내부 수업 자료 `source`로 위장하지 않는다.
3. 코드 편집기에 실행용 복사본을 넣되 상단 주석에 원작 URL·커밋·파일과 교사 호환 변경을 적고 팀 시작 버전으로 저장한다. 학생 작업은 이 기준 뒤부터 기록한다.
4. 팀 저장소는 교사가 별도로 준비하고 원작 `LICENSE.txt`와 출처 설명을 함께 둔다. Python 파일만 복사한 새 저장소로 배포를 끝내지 않는다.
5. 학생은 각자 초안 → 변경 제안 → 동료 검토 → 팀 반영을 진행하고, GitHub에는 팀 확정 버전을 별도 PR로 제출한다.

현재 다운로드는 `main.py` 한 파일이며(`Workspace.jsx:116`), GitHub PR 생성도 등록한 `binding.path` 한 파일의 내용만 변경한다(`server/classroom/github.js:147`). 따라서 **출처 주석을 남겼다고 전체 MIT 허가 문구가 자동 포함되는 것은 아니다.** 교사가 팀 저장소의 라이선스 파일을 준비하고 보존해야 한다. 기존 저장소의 다른 파일을 보존하는 동작과 누락된 라이선스 파일을 새로 생성하는 동작도 구분해야 한다.

| 3. 반례 검토 | “벽 바로 옆에서 시작하면?” 질문, 동료 리뷰 예시 한 번 | 시작 위치·크기 두 조건을 스스로 정하고 실패 여부 판단 | 자기 가설에 불리한 조건도 검사함 |
| 4. 도움 줄이기 | 값 후보와 리뷰 문장 틀을 없앰 | 추가 변경 한 가지·보완 요청·선택 이유를 자기 말로 작성 | 예시 없이 선택과 거절 이유를 설명함 |
| 5. 새 문맥 전이 | “같은 방에서 다른 크기 물체의 안전 거리” 등 맥락만 제시 | 필요한 경계 수정과 관찰 조건을 정하고 원작과 다른 목적 설명 | 원작을 다시 복사하지 않고 어떤 구조를 재사용할지 판단함 |

원작을 복사한 뒤 즉시 자유 확장 과제를 주면 설명하지 못하는 코드가 많아질 수 있다. 우선 “한 학생 한 값 변경”으로 작게 시작하고, 다음 제안에서는 실험·작성 담당과 반례 검토·출처 기록 담당을 교대해야 한다. 검토·기록 담당자도 최소 한 번 조건을 예측·검증하고 코드 제안을 작성하도록 한다.

AI 선택 수업에서는 “원작을 설명해 달라”는 도움과 생성된 코드를 구분해 `AI 제안과 나의 판단`에 기록한다(`EvidenceForm.jsx:14`). AI 없는 수업에서도 같은 원작 읽기·실험·반례·동료 검토를 사용하고 그 칸을 요구하지 않는다. AI가 모든 코드를 다시 작성하는 것은 이 과제의 입문 범위를 벗어난다.

## 교사 피드백 질문과 판단 근거

| 관점 | 학생에게 묻는 질문 | 함께 볼 기록 |
| --- | --- | --- |
| 원작 이해 | “이 줄을 지우면 어떤 변화가 생기나요? 실행 전에 예상해보세요.” | 원작 고정 파일, 질문 이슈, 가설 |
| 최소 변경 | “바꾼 한 줄과 그대로 둔 부분은 무엇이며 왜 나눴나요?” | 시작 버전 대비 diff, 교사 호환 수정 메모, 학생 제안 |
| 검증 | “지금 설명이 틀렸다고 판단할 결과는 무엇인가요?” | 경계 반례, 실제 실행 조건·관찰 |
| 협업 | “동료의 어떤 지적을 반영했고, 반영하지 않은 의견에는 어떤 근거가 있나요?” | 보완 요청·재제안·승인, 판단 이유 |
| 전이 | “방 크기 대신 공 크기가 바뀌면 어느 계산을 다시 확인해야 하나요?” | 새 조건의 가설과 실험, 다음 계획 |
| 저자와 라이선스 계승 | “원작 저자는 누구인가요? 어느 버전·파일을 썼나요? 받은 조건은 어디에 남겼나요?” | 고정 출처, 원작 `LICENSE.txt`, 팀 저장소의 출처 설명·라이선스 파일 |
| 학생 기여 | “원작·교사 준비·본인·동료가 한 일을 각각 보여줄 수 있나요?” | 초기 코드, 이후 diff, 개인 초안·제안, GitHub 작성자/제출자와 로컬 검토 |

학생 기여를 커밋 줄 수·PR 개수·복사된 코드의 완성도로 점수화하지 않는다. 말로 설명한 판단과 반례를 찾은 기여도 기록한다. 미확인 GitHub 작성자를 이름·이메일만으로 학생에게 연결하지 않는 현재 원칙(`store.js:83`, `learning-feedback.js:34`)을 유지한다.

## 우선 보완 제안

1. **공개 리믹스 전용 출처 구조와 화면**: 저장소 URL, 고정 커밋, 파일, 원작자·라이선스 원문 링크, 호환 수정, 원작 불변 스냅샷을 구분해 저장. 가짜 내부 `example` 연결을 만들지 않기.
2. **교사 사전 호환 검사와 시작 기준 고정**: 지원 API 차이·외부 패키지·무한 반복을 검토하고 교사 준비 부분을 첫 학생 제안의 기여와 분리하기.
3. **출처와 라이선스가 함께 이동하는 내보내기**: 코드 한 파일을 내려받거나 제출할 때 라이선스가 빠질 수 있음을 해결하고 원작·학생 변경 설명을 보존하기.
4. **쉬운 리믹스 과제 카드**: 읽어야 할 구간·수정 가능 한 줄·관찰 조건·반례·역할 교대·도움 축소를 교사가 설정하기.
5. **기여 구별을 돕는 교사 보기**: 원작 대비 변경, 교사 호환 수정, 학생별 제안과 리뷰를 함께 보여주되 저작권이나 학습 성취를 자동 확정하지 않기.

기존 협업 기반은 재사용할 수 있다. 우선 필요한 것은 더 어려운 코드를 추가하는 일이 아니라, 외부 코드를 어떤 조건으로 가져왔고 학생이 그 위에서 무엇을 이해·검증·개선했는지 확인할 경로다.
